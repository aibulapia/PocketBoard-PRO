## ✅ v2.5 구현 완료 (10건)

### 1. 안전보고문 폭염작업 대책 자동 작성 — 구현됨
- 공사전 복사: 그날(06시 체계) **최초 기록** 체감온도 자동 삽입
- 공사중 복사: **12:00~14:00 사이 최초 기록** 자동 삽입
- 형식: `*폭염대책 : 체감온도 31.9℃ (관심)` + 단계별 조치 문구 (31℃ 이하도 작성)
- 온도는 전 화면 **소수점 첫째자리** 통일 (카드/칩/보고문)
- 해당 시간대 기록 없으면 → **경고 팝업** 표시, 복사 중단

### 2. 기상 정보 팝업 — 구현됨
- 헤더 🌤️ 버튼 → 팝업 (울산 북구 양정동, nx=103/ny=84)
- 실황 기온·습도(초단기실황 API) + 특보 라벨 자동 추출 + 통보문/속보 원문(탭 펼침)
- 2시간 캐시, 10분마다 TTL 확인, 마지막 갱신시각 표시, 실패 시 캐시 유지
- ⚠️ **첫 실배포 후 휴대폰에서 동작 확인 필요** (CORS/응답 필드는 실환경에서만 최종 검증 가능)

### 3. 카톡 인앱브라우저 우회 + 홈화면 설치 안내 — 구현됨
- 카톡 UA 감지 → Android: kakaotalk 외부열기 스킴 + intent 폴백 자동 실행
- iOS: 전체화면 안내 오버레이 ("⋯ → 다른 브라우저로 열기")
- PWA 설치 배너 (최초 1회): Android 원클릭 설치 / iOS 단계 안내

### 4. 마스터 코드 (관리자 모드) — 구현됨
- 공사코드 모달 하단 "🔑 관리자 모드" 진입
- **서버측(RPC) 코드 검증** — supabase-master-v3.sql 적용 필요
- 기능: 현장(세션) 등록소 관리(등록/삭제/열기), 전체 통합 엑셀, 연락처 관리
- 연락처는 **서버에만 보관** — 일반 사용자 기기에 미전송

### 5. 엑셀 저장 + 구글시트 자동백업 — 구현됨
- 일반: 헤더 📊 버튼 → 현재 세션만 엑셀 다운로드
- 마스터: 전체 현장 통합 엑셀 (세션별 시트 탭)
- 자동백업: Apps Script **매일 06시 트리거** (apps-script-v3.gs) — 등록소 세션 전체를 일자별 백업 탭에 기록

### 6. 작업연장 버튼 — 구현됨
- 바텀시트 ⏰ 작업연장: 18~23시·00~05시 1시간 단위 선택 (기본 17시, 평소 비노출)
- 표기 "OO시연장" 통일 (예: 22시연장, 01시연장)
- 17시 이후 목록: "공사중" 배지 자리 → 연장없음 "종료"(회색) / 연장 "OO시연장"(남색)
- 카톡 복사·안전보고문에 자동 반영

### 7. TODAY 배지 터치 토글 — 구현됨
- TODAY 배지 직접 터치 → 파란/흰글씨 ↔ **회색/이탤릭** 전환
- 06시 지나면 자동 리셋, 재터치로 복귀

### 8. TODAY "n일째" 표시 — 구현됨
- **실제 작업일 기준**: 하루 끝(06시)에 TODAY 활성이었던 날만 +1 (수동취소일 제외)
- 최초 인식 시 엑셀 요일 데이터로 소급 초기값 / 긴급공사는 등록일부터
- 2일째부터 표시 ("TODAY 2일째")

### 9. 감독자·공장 데이터 외부화 (B-1) — 구현됨
- `data.js` 신규: 감독자 명단/공장/하위공장/작업유형 안전대책/층수탭/공통수칙
- ⚠️ 이름만 허용, 연락처 절대 금지 (파일 상단 경고 주석)
- _headers 캐시 1시간으로 조정 → 명단 수정 배포가 빠르게 반영

### 10. 일일 리셋 (06시 체계) — 구현됨
- 하루 = 06:00 ~ 익일 05:59 로 전체 통일
- 06시 경과 시: 공사중→확인필요, 연장 초기화, TODAY 취소 리셋, 체감온도 표시 리셋
- 체감온도 **데이터는 보존**(숨김만) — 백업/이력에 활용

- **기존**: 18~23시, 0~5시 버튼을 가로로 늘어놓고 터치하는 방식

  - 체감온도가 있으면 포함, 없으면 그 항목만 생략

## ✅ v2.24c 구현 완료 (2026-08-06)

### 관리자 모드 팝업이 30일 캐시 로그인을 못 알아보던 버그
- **증상**: 30일 캐시로 이미 로그인(관리자/최고관리자)돼 있어도, "🔑 관리자(마스터) 모드"
  팝업을 열면 매번 코드 입력 화면부터 다시 나옴. 그 안쪽에 있는 "인증 해제"(로그아웃)
  버튼에 사실상 도달하기 어려움 — 실사용 중 발견됨("인증 해제 버튼이 안 보인다")
- **원인**: 인증 상태가 두 개로 나뉘어 있었음
  - `masterLevel` / `adminAuthed` — 30일 캐시, 앱 새로 열 때 정상 복원됨
  - `masterAuthed` — 관리자 모드 팝업 **안에서만** 쓰는 별도 상태, 항상 `false`로 시작하고
    팝업을 닫을 때(`closeMaster`)마다 다시 `false`로 리셋됨 → 캐시와 동기화 안 됨
- **수정**: `masterAuthed` 상태 완전 제거, 이미 있는 `masterLevel > 0`(캐시 기반)으로 통일.
  관리자(레벨1)·최고관리자(레벨2) 공통 적용 (같은 팝업 진입 조건을 같이 쓰는 구조라
  별도 분기 불필요했음)
- **검토했다가 최종 보류한 대안**: "로그인 유지한 채 하위 레벨 화면만 임시로 미리보기"하는
  기능도 함께 논의했으나(레벨2는 감독자/일반관리자 두 단계, 레벨1은 감독자 한 단계),
  **"권한 계층이 이미 하위 레벨을 전부 포함하는 구조라, 화면 확인용으로는 불필요하고
  인증 해제만으로 충분하다"는 결론으로 제외**
- **검증**: masterLevel 0/1/2 세 가지 상태로 렌더 테스트 — 로그인화면·인증해제버튼 노출,
  버전 표시 문구 전부 기대값과 일치 확인. `adminLogout()`이 이미 `masterLevel`을 0으로
  되돌리는 것도 재확인해 연쇄 영향 없음 확인

### C. 오프라인 지원 (PWA 오프라인 모드)

> 앱 구조를 꽤 크게 건드리는 작업 — "큰 변화" 규칙 적용.
> 지금은 서비스워커가 아예 없어서 인터넷 끊기면 화면조차 안 뜸.

**핵심 전제 (2026-08-04 확인)**: **공사 1개 = 감독자 1명이 항상 전담, 100% 지켜짐, 겹칠 일 없음.**
→ 따라서 여러 사람 기록이 충돌해서 병합해야 하는 상황 자체가 없음. 복잡한 병합 로직 불필요.

**목표 — 오프라인에서도 온라인과 동일하게 작업**

| 온라인 때 하던 것 | 오프라인에서 |
|---|---|
| 목록 조회 | 마지막으로 받아둔 목록 그대로 보임 |
| 바텀시트 입력 (체감온도·상태·연장·메모 등 전부) | **온라인과 완전히 동일하게** 입력 가능 |
| 저장 | 기기 안에 저장 + "오프라인 저장됨" 표시 |
| — | 인터넷 복귀 시 대기 중인 기록을 **자동으로 순서대로 서버에 전송** |

**필요한 기술 요소**
- **서비스워커 신규 도입** — 지금 전혀 없음. `public/sw.js` **신규 파일** 생성 필요.
  앱 껍데기(index.html, data.js, config.js, storage.js, 아이콘)를 캐싱해서
  오프라인에도 화면이 뜨게 함
- **마지막 목록 로컬 저장** — 성공적으로 받아온 공사 목록을 기기에 저장해두고,
  오프라인일 때 이걸로 화면 표시
- **오프라인 쓰기 대기열** — 기록 시도 시 네트워크 실패하면 기기에 대기시켜두고
  "저장 대기 중" 표시. 온라인 복귀 감지되면 **그대로(병합 없이) 순서대로** 전송
  — 감독자 1명 전담 원칙 덕분에 남의 기록과 겹칠 일이 없으므로 단순 재생(replay)이면 충분
- **온라인 복귀 감지** — 브라우저의 "온라인/오프라인" 신호만으론 부정확할 수 있어,
  실제로 서버에 요청이 성공하는지도 같이 확인
- **약한 신호 대응** — 요청 실패 시 자동으로 몇 번 재시도
- **오래된 대기열 기록 처리** (2026-08-04 확정): **그대로 자동 전송, 사람 확인 없음**
- **서비스워커 캐시 무효화**: 캐시 이름에 `APP_VERSION`을 포함시켜, 배포마다 버전이
  바뀌면 새 캐시로 자동 교체되고 오래된 캐시는 자동 정리되도록 구현

**UI/UX 필요사항**
- 오프라인 상태임을 알려주는 표시 (상단 배지 등)
- 기록마다 "저장됨(오프라인)" / "동기화 완료" / "전송 실패" 상태를 명확히 구분 —
  안전 데이터라 신뢰 중요
- 오래된(캐시된) 목록을 보고 있을 때 "최신 정보 아닐 수 있음" 경고

### 5. 사진 촬영 + 구글 드라이브 백업
- **권한**: `masterLevel >= 1` (일반관리자 이상, 일반 감독자는 대상 아님)
- **진입 경로**: 관리자가 기존 공장 탭(1~5공장 등)에서 공장 선택 → 공사 항목 선택 →
  상세화면(바텀시트) 안에 촬영 버튼
- **촬영 방식**: 카메라 즉석 촬영만 (갤러리에서 기존 사진 선택 불가)
- **폰 사진첩**: 촬영 원본은 그대로 1장 유지 (이름 안 건드림, 앱이 사진첩 파일명 변경 불가하므로)
- **클라우드 백업**: 기존 `apps-script-v3.gs` 확장 → 실장님 구글 드라이브에 **공장별 폴더**로 저장
  (Drive는 서버 측에서 이름·폴더를 직접 지정 가능해 제약 없음)
- **드라이브 폴더 구조** (2026-08-02 확정): 공장별로만 분리, 그 안에 그 공장 사진 전부
  ```
  [실장님 구글 드라이브]
   ├─ 1공장/  → OO공사_20260802_1.jpg, XX공사_20260802_1.jpg ...
   ├─ 2공장/  → ...
   └─ (공장별로 계속)
  ```
  공장 폴더는 미리 만들 필요 없이, Apps Script가 첫 업로드 시 없으면 자동 생성
- **파일명 규칙**: `공사명_촬영일자_순번` (예: `OO공사_20260802_1`)
- **순번 중복 방지** (2026-08-02 확정): 같은 공사를 여러 감독자가 같은 날 동시에 찍어도
  순번이 겹치지 않도록, Apps Script가 저장 직전 해당 폴더에서 같은 `공사명_날짜` 접두사를
  가진 기존 파일을 확인해 다음 번호를 자동으로 매김 (기기별 로컬 카운트 아님)
- **열람 권한**: 드라이브 폴더 주인(실장님)은 전체 열람 가능. 현장 감독자끼리는 서로 못 봄
  (각자 폰에는 본인이 찍은 사진만 보임)
- **장수 제한**: 없음. 다만 10장 이상 누적되면 "저장공간을 위해 꼭 필요한 사진만
  남겨주세요" 안내 문구만 표시 (차단은 아님)
- **비교 검토했던 대안**:
  - Supabase Storage 신규 구축 → 무료 요금제 1GB 저장 / 5GB 트래픽 한도로 가능은 하나,
    구글 드라이브가 이미 쓰는 Apps Script 경로를 재사용할 수 있어 채택 안 함
  - 폰 로컬(IndexedDB)에만 저장 → 기기 변경·삭제 시 유실, 다른 감독자·관리자 열람 불가로
    보류 후 구글 드라이브안으로 최종 변경
- **착수 전 필요 작업**: `server/apps-script-v3.gs` 수정 코드 작성 후,
  실장님이 Apps Script 쪽에서 **직접 재배포**해야 함 (구글시트 백업 설정 때와 동일 방식).
  완성 후 실장님 실제 폰으로 촬영·업로드 테스트 필요.

> 지금 쓰는 공사 코드를 등록소에 하나 등록하는 것만으로 해결(코드 작성 불필요, 관리자 모드
> 팝업의 "등록" 버튼 사용). 실장님 판단으로 2026-08-06 보류 확정 — 필요해지면 재확인.

### C. 세션 구조 재설계 — 상세 (2026-07-22 확정)

**왜 필요한가**
지금은 공사 코드(세션) 하나에 공사 목록과 진행상황이 통째로 같이 저장됨 → 공사 코드를 바꾸면
목록 자체가 통째로 바뀌거나 비어 보임. 여러 팀이 **같은 공사 목록**을 보되 "우리 팀은 여기까지
했다"는 체크(진행상황)는 팀마다 따로 남아야 하는 상황이 생기면, 지금 구조로는 한쪽이 체크하면
다른 팀 화면에도 그대로 바뀌어 보여 불가능함.

**확정된 사양**

| 항목 | 확정 내용 |
|---|---|
| 공사 코드가 구분하는 것 | **팀/현장별** (담당자별·날짜별 아님 — 여러 팀이 같은 목록을 각자 진행) |
| 진행상황 분리 범위 | **전체** — 상태(공사중/종료), 체감온도 기록, TODAY, 연장, 메모 |
| 공통 공사목록 업로드 | 관리자가 **기존 방식 그대로**(초기화 후 엑셀 "파일 변경")로 올림 → 전체 팀에 공유 |
| 새 엑셀 올리면 | 모든 팀의 진행상황 **전부 초기화** |

**구현 방안 (당시 유력했던 안)**
- 방안 2 — 공통목록을 `__master__` 같은 고정 세션에 저장, 팀 코드 세션엔 **진행상황만** 저장.
  앱 로드 시 공통목록을 불러온 뒤 팀 진행상황을 덮어씌우는 방식.
  (방안 1: 목록/진행상황 테이블 완전 분리 — 더 깔끔하지만 변경 폭 큼, 채택 안 함)

**착수 전 아직 안 정한 것**
- 기존 `default` 세션 데이터를 새 구조로 마이그레이션할지 여부

**착수 조건**
실제로 여러 팀이 각자 공사 코드로 나눠 쓰게 될 때. 그 전까진 `default` 세션 하나로 계속 사용.

**연관 작업**: 최근(2026-08-02) 위크매치(WeekMatch, 평일용 배정 앱)와의 연동 설계 논의에서,
**B-2(감독자·공장 명단 Supabase 테이블화)가 먼저 끝나야** 두 앱 연동이 가능하다고 확인됨.
세션 재설계도 같은 데이터 구조를 건드리는 작업이라, B-2 → C 순서로 진행하는 게 자연스러움.
