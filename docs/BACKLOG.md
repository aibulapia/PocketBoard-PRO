## 🔴 미해결 — 이미 예전 서비스워커에 갇힌 기기

- **증상**: 홈화면 아이콘 실행 시 ERR_FAILED. 여러 감독자에게서 보고됨(2026-08-13)
- **원인**: 예전 `sw.js`가 캐시를 우선 반환하고, 백그라운드 캐시 갱신도 조건에 걸려
  동작하지 않음 → 새 버전을 배포해도 그 기기는 영원히 옛 파일만 봄 (3회 접속 테스트로 확인)
- **불가능한 방법**: 서버/Cloudflare 프로젝트를 새로 만들어도 **주소가 같으면 무효**
  (캐시는 주소 단위로 저장됨)
- **가능한 방법 2가지**
  1. 새 주소로 전환 (`/app.html` 같은 파일명 변경 또는 새 프로젝트+새 주소)
     → 감독자는 새 링크 한 번 클릭 후 홈화면 추가. 새 주소에는 캐시가 없어 즉시 정상 동작
  2. 기기별 수동 정리 (설정 → 앱 삭제 → 크롬 사이트 데이터 삭제 → 재접속)
     → 인원이 많으면 비현실적
- **현재 상태**: 실제 피해 규모 파악 중(카톡 오픈채팅 등으로 증상 확인 예정).
  소수면 개별 안내, 다수면 새 주소 전환으로 결정 예정

## ✅ v2.52 구현 완료 (2026-08-11)

### 🐛 홈화면 아이콘(PWA)에서 ERR_FAILED 반복되던 문제 수정
- 서비스워커 fetch 처리에서 오류가 나면 무조건 던지던 것을 전부 예외 안전하게 재작성
- fallback 화면을 고정 `Response` 객체 재사용 → 매번 새로 만드는 함수로 변경
  (`Response`는 body를 한 번 읽으면 재사용 불가 — 두 번째 요청부터 오류 발생하던 문제)
- 캐시·네트워크 둘 다 실패해도 브라우저 자체 오류화면 대신 앱 내 안내 화면 표시

### PWA 앱 설치 기능 제거
- `beforeinstallprompt` 핸들러·설치 배너 UI·관련 상태 전부 제거
- `sw.js`(오프라인 캐시)와 `manifest.json`의 `display: standalone`은 유지
  — 앱 설치 기능과 서비스워커 캐시는 별개, 홈 화면 바로가기에 필요

### 버전 체크 및 자동 업데이트
- `public/version.json` 신설, 앱 실행 시 서버 최신 버전과 비교
- 구버전이면 캐시·서비스워커 정리 후 강제 재로딩
- `sessionStorage` 플래그로 무한 새로고침 방지, 네트워크 오류 시 현재 버전 유지
- `version.json`은 `_headers`·`sw.js` 양쪽에서 캐시 금지

### 프로그램 정보 화면
- "🔄 공사목록 업데이트 — 주 2회 · 수/금 오후" 추가

### 배포용 주석 정리 (index.html)
- Babel 파서(AST) 기반 안전 제거 — 문자열·URL 손상 없음
- 244KB → 150KB (38% 감소), 3563줄 → 3294줄
- 원본은 `index.html.backup-comments-v2_5h`로 백업

### 보안 — 소스에 노출된 비밀번호 값 제거
- `index.html` 주석의 암호 원본값, `server/`·`docs/` 문서·SQL의 백업 토큰 값 전부 제거 (6곳)

### 5. 사진 촬영 + 구글 드라이브 백업
- **권한**: `masterLevel >= 1` (일반관리자 이상, 일반 감독자는 대상 아님)
- **진입 경로**: 관리자가 기존 공장 탭(1~5공장 등)에서 공장 선택 → 공사 항목 선택 →

- **촬영 방식**: 카메라 즉석 촬영만 (갤러리에서 기존 사진 선택 불가)
- **폰 사진첩**: 촬영 원본은 그대로 1장 유지 (이름 안 건드림, 앱이 사진첩 파일명 변경 불가하므로)
- **클라우드 백업**: 기존 `apps-script-v3.gs` 확장 → 실장님 구글 드라이브에 **공장별 폴더**로 저장
  (Drive는 서버 측에서 이름·폴더를 직접 지정 가능해 제약 없음)
- **드라이브 폴더 구조** (2026-08-02 확정): 공장별로만 분리, 그 안에 그 공장 사진 전부

  ```
   ├─ 1공장/  → OO공사_20260802_1.jpg, XX공사_20260802_1.jpg ...
   ├─ 2공장/  → ...
   └─ (공장별로 계속)
  ```
  공장 폴더는 미리 만들 필요 없이, Apps Script가 첫 업로드 시 없으면 자동 생성
- **파일명 규칙**: `공사명_촬영일자_순번` (예: `OO공사_20260802_1`)
- **순번 중복 방지** (2026-08-02 확정): 같은 공사를 여러 감독자가 같은 날 동시에 찍어도
  순번이 겹치지 않도록, Apps Script가 저장 직전 해당 폴더에서 같은 `공사명_날짜` 접두사를
  가진 기존 파일을 확인해 다음 번호를 자동으로 매김 (기기별 로컬 카운트 아님)
- **열람 권한**: 드라이브 폴더 주인(실장님)은 전체 열람 가능. 현장 감독자끼리는 서로 못 봄
  (각자 폰에는 본인이 찍은 사진만 보임)
- **장수 제한**: 없음. 다만 10장 이상 누적되면 "저장공간을 위해 꼭 필요한 사진만
  남겨주세요" 안내 문구만 표시 (차단은 아님)
- **비교 검토했던 대안**:
  - Supabase Storage 신규 구축 → 무료 요금제 1GB 저장 / 5GB 트래픽 한도로 가능은 하나,
    구글 드라이브가 이미 쓰는 Apps Script 경로를 재사용할 수 있어 채택 안 함
  - 폰 로컬(IndexedDB)에만 저장 → 기기 변경·삭제 시 유실, 다른 감독자·관리자 열람 불가로

- **착수 전 필요 작업**: `server/apps-script-v3.gs` 수정 코드 작성 후,
  실장님이 Apps Script 쪽에서 **직접 재배포**해야 함 (구글시트 백업 설정 때와 동일 방식).

**로그인(인증) 넘기기 — 짝짓기 코드 방식 채택**

`.pages.dev` 기본 주소는 브라우저가 "공용 도메인"으로 취급해 **쿠키·localStorage가
서로 다른 앱끼리 자동 공유되지 않음** (실제 도메인 구매 전까진 구조적 제약).
→ 코드 발급 방식으로 우회:

```
[메인 앱] 관리자 로그인 성공
   → 서버가 6자리 코드 발급 (5분 유효, 1회용)
   → 화면에 코드 표시
[마스터 앱] 코드 입력
   → 서버가 코드 확인 → 로그인 처리 (마스터 앱에도 30일 캐시 별도 저장)
```

- 신규 Supabase 테이블: `pairing_codes` (코드, 권한레벨, 생성시각, 만료시각, 사용여부)
- 신규 RPC 2개: `master_issue_pairing_code`(발급) / `verify_pairing_code`(검증+소멸)
- 메인 앱에 "코드 발급" 버튼 추가 필요 (관리자 로그인 성공 화면, 레벨1 이상에게만 노출)
- 코드는 1회용 + 5분 후 자동 무효화로 노출 위험 최소화

**착수 전 확정해야 할 것**
- 사진 기능 권한 레벨 재확인 (레벨1 포함 여부, 위 경고 참고)
- 새 Cloudflare Pages 프로젝트명·주소
- `logic.js`로 옮길 함수 목록 확정 (그렙 전수조사로 06시 관련 함수 전부 식별 필요)
- 짝짓기 코드 자릿수(6자리 가정)·유효시간(5분 가정) 확정

### C. 세션 구조 재설계 — 상세 (2026-07-22 확정)

**왜 필요한가**
지금은 공사 코드(세션) 하나에 공사 목록과 진행상황이 통째로 같이 저장됨 → 공사 코드를 바꾸면
목록 자체가 통째로 바뀌거나 비어 보임. 여러 팀이 **같은 공사 목록**을 보되 "우리 팀은 여기까지
했다"는 체크(진행상황)는 팀마다 따로 남아야 하는 상황이 생기면, 지금 구조로는 한쪽이 체크하면
다른 팀 화면에도 그대로 바뀌어 보여 불가능함.

**확정된 사양**

| 항목 | 확정 내용 |
|---|---|
| 공사 코드가 구분하는 것 | **팀/현장별** (담당자별·날짜별 아님 — 여러 팀이 같은 목록을 각자 진행) |
| 진행상황 분리 범위 | **전체** — 상태(공사중/종료), 체감온도 기록, TODAY, 연장, 메모 |
| 공통 공사목록 업로드 | 관리자가 **기존 방식 그대로**(초기화 후 엑셀 "파일 변경")로 올림 → 전체 팀에 공유 |
| 새 엑셀 올리면 | 모든 팀의 진행상황 **전부 초기화** |

**구현 방안 (당시 유력했던 안)**
- 방안 2 — 공통목록을 `__master__` 같은 고정 세션에 저장, 팀 코드 세션엔 **진행상황만** 저장.
  앱 로드 시 공통목록을 불러온 뒤 팀 진행상황을 덮어씌우는 방식.
  (방안 1: 목록/진행상황 테이블 완전 분리 — 더 깔끔하지만 변경 폭 큼, 채택 안 함)

**착수 전 아직 안 정한 것**
- 기존 `default` 세션 데이터를 새 구조로 마이그레이션할지 여부

**착수 조건**
실제로 여러 팀이 각자 공사 코드로 나눠 쓰게 될 때. 그 전까진 `default` 세션 하나로 계속 사용.

**연관 작업**: 최근(2026-08-02) 위크매치(WeekMatch, 평일용 배정 앱)와의 연동 설계 논의에서,
**B-2(감독자·공장 명단 Supabase 테이블화)가 먼저 끝나야** 두 앱 연동이 가능하다고 확인됨.
세션 재설계도 같은 데이터 구조를 건드리는 작업이라, B-2 → C 순서로 진행하는 게 자연스러움.
