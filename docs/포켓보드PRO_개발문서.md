# 2. 아키텍처 — 왜 이렇게 만들었나

## 2-1. 왜 단일 HTML 파일인가

현장 감독자들이 **앱스토어 설치 없이 링크 하나로 즉시** 쓸 수 있어야 했습니다.
빌드 과정이 없으므로 파일 하나만 교체하면 배포가 끝납니다.

**대가로 감수한 것**
- 파일이 3,700줄로 매우 큼 (모듈 분리 불가)
- 브라우저가 매번 Babel로 변환하므로 첫 로딩이 조금 느림
- 코드가 그대로 공개됨 → **비밀값을 앱에 둘 수 없음**(7장 참고)

## 2-2. 왜 로그인이 없는가

주말 현장에서 감독자가 **바로 열어 바로 점검**해야 합니다.
로그인 절차가 있으면 현실적으로 안 씁니다.

대신 권한이 필요한 기능(연락처 조회, 초기화 등)만 **코드 입력**으로 엽니다.

## 2-3. 데이터를 한 덩어리로 저장하는 구조

공사 목록 전체가 `pocket_sessions` 테이블의 **한 행, 한 JSON 배열**에 들어갑니다.
(`session_id = 'default'` 고정 — 예전엔 공사코드별로 나눴으나 v2.5c에서 폐지)

**장점**: 구조가 단순하고 조회가 한 번에 끝남
**단점**: 여러 사람이 동시에 저장하면 서로 덮어쓸 위험 → **6-4 병합 규칙**으로 해결

# 6. 기술 사양 — 정확한 동작 규칙

> **이 장이 이 문서의 핵심입니다.** 재구현 시 이대로 만들면 동일하게 동작합니다.

## 6-1. 06시 일일 체계 (이 앱의 심장)

**규칙**: 하루의 경계는 자정이 아니라 **오전 6시**입니다.

```js
const WORKDAY_SHIFT_MS = 6 * 60 * 60 * 1000;   // 6시간
workday = (현재시각 - 6시간) 의 날짜
```

- 8/27 새벽 3시 → workday는 **8/26** (아직 전날 근무)
- 8/27 오전 7시 → workday는 **8/27**

**06시가 지나면 자동으로 초기화되는 것**
- `status: checked` → `pending` (공사중 → 공사전)
- `extendHour` → `null` (연장 해제)
- `todayOn` → `null` (수동 TODAY 해제)
- `collapsedOn` → `null` (v2.70 — 접어둔 카드 다시 펼침)

**판정 기준**: 카드의 `dayKey`가 현재 `workday`와 다르면 "하루 지났다"로 봅니다.

⚠️ **반드시 `TZ=Asia/Seoul` 기준**. UTC로 계산하면 날짜가 어긋납니다.

## 6-1a. TODAY 켜짐과 카드 펼침 (v2.57~v2.70)

**TODAY가 켜졌는지 판정하는 순서** (`isTodayActive`)

1. `todayForceOff === true` → **꺼짐.** 사람이 직접 껐으므로 날이 바뀌어도 꺼진 채
2. `todayOn === workday` → **켜짐.** 사람이 직접 켬
3. 둘 다 아니면 → 엑셀에 오늘 인원이 있는지로 **자동 판단**

**카드가 펼쳐지는 조건** (v2.70)

```
펼침 = (오늘 화면이고 TODAY 켜짐  또는  공사중)  그리고  그 날 접지 않았음
```

- `공사중` = `status === "checked"` 이고, 17시가 지났다면 연장이 잡혀 있을 것
- 접기 기록은 `collapsedOn`에 그 날 workday를 적음. 날이 바뀌면 값이 달라져 저절로 다시 펼쳐짐
- 다른 날짜를 넘겨볼 때(`dateOffset ≠ 0`)는 오늘 기준 TODAY로 펼치지 않음

> v2.57까지는 **사람이 직접 켠 TODAY만** 펼침 조건이었습니다.
> v2.57에서 자동 켜짐이 생기면서 두 규칙이 부딪혀 대부분의 카드가 접힌 채로 남았고,
> v2.70에서 자동 켜짐도 펼침에 포함하도록 바로잡았습니다.

**공장 탭의 앞 숫자**는 펼침 여부와 무관하게 `TODAY 또는 공사중` 건수로 셉니다.
카드를 접어도 숫자는 줄지 않습니다.

## 6-1b. 공사중 전환과 허가번호 (v2.70)

- `입력 완료`를 누르면 **공사위치·담당감독자 중 하나만 채워져 있어도** `status: checked`가 됩니다.
  담당감독자는 엑셀에서 자동으로 들어오는 경우가 많아, 둘 다 요구하면 공사위치를 적지 않았을 때
  계속 `공사전`에 머무는 문제가 있었습니다.
- 안전보고문의 `*허가번호`는 **보고문을 만드는 날의 연·월**로 계산합니다.
  2026년 9월 → `2609`, 10월 → `2610`, 2027년 1월 → `2701`.
  (v2.57까지는 `2607`이 코드에 그대로 박혀 있었습니다.)

## 6-1c. 공사 정리와 병합 (v2.71)

**왜 지우면 안 되는가**

저장은 항상 `서버 최신본과 합쳐서` 올립니다(`mergeByUpdatedAt`).
합치는 규칙은 **id 기준 합집합**이며, 서버에만 있는 공사는 그대로 살아남습니다.
따라서 어떤 기기가 목록에서 공사를 빼도, 저장하는 순간 서버 것이 되살아납니다.

v2.70까지는 `applyDailyCycle`이 기간 지난 공사를 각 기기에서 지웠기 때문에
지움 ↔ 되살아남이 무한 반복되어 목록이 깜빡였습니다.

**v2.71 방식**

- 공사를 없애지 않고 `removedAt`(치운 시각, ms)을 붙입니다
- 이 값은 공사 객체의 일부이므로 병합 시 함께 넘어가고, `updatedAt`이 더 새로우므로 이깁니다
- 화면(`filteredItems`)과 공장 탭 숫자 양쪽에서 `removedAt`이 있는 공사를 제외합니다
- 정리·완전삭제는 **마스터 기기에서만** 수행합니다.
  감독자 기기는 목록을 건드리지 않으므로 부딪힐 일이 없습니다
- 치운 지 30일(`REMOVED_KEEP_DAYS`)이 지나면 배열에서 완전히 제거합니다
- 전체 초기화(`doReset`)도 빈 배열 덮어쓰기 대신 전부 `removedAt` 표시로 처리합니다

**되살리기는 없습니다.** 엑셀을 다시 올리면 `mergeItems`가 `removedAt`을 보존하지 않으므로
표시가 자연히 풀려 목록에 다시 잡힙니다.

> ⚠️ 정리 관련 코드는 `masterLevel` **선언 뒤에** 두어야 합니다.
> 앞에 두면 렌더 도중 참조해 앱이 시작되지 않습니다(v2.56a와 같은 사고).

## 6-2. 정렬 규칙 (v2.55에서 전면 개편)

**탭에 따라 완전히 다릅니다.**

### v2.72a부터 — 전체 탭·개별 공장 탭 **공통**
```
1순위: 그 날 공사 먼저 (엑셀 인원 있음 또는 pinnedDates에 그 날짜가 있음)
2순위: 공장순 — SUPPORTED_FACTORIES 순서 (1공장 → … → 6 PT → 7 소재 → 8 아산 → 9 기타)
3순위: 사업장순 — 프레스 → 차체 → 도장 → 의장 → 엔진 → 변속기 → 실린더 → PDI → (그 외)
4순위: 즐겨찾기(★), 마스터는 ★중요
5순위: 엑셀 순서
```

진한 묶음과 흐린 묶음 **각각 안에서** 같은 규칙으로 돕니다.
개별 공장 탭은 한 공장뿐이라 2순위가 결과에 영향을 주지 않습니다(코드는 공통).

> v2.72에는 공장순이 없어, 「전체」 탭에서 사업장은 맞게 도는데
> 공장이 뒤섞여 보이는 문제가 있었습니다.

그 날 공사가 아닌 카드는 **흐리게(opacity 60%) + 이탤릭**으로 낮춰 표시하고,
점선 테두리 `TODAY` 배지를 눌러 그 날 공사로 당겨올 수 있습니다(`pinnedDates`).
`pinnedDates`는 날짜별 목록이므로 다른 날에는 영향을 주지 않습니다.

> v2.71까지는 「전체」 탭이 **엑셀 순서만** 따랐고, 개별 탭은 **사업장순이 1순위**였습니다.

사업장 판정은 `company` 값에 해당 단어가 **포함**되는지로 봅니다.
(예: `변속기케이스1` → "변속기"에 걸림)

> ⚠️ 이전(v2.54까지)에는 **공사명(title)**에 "프레스/차체/도장/의장"이 들어갔는지로
> 정렬했습니다. 이 때문에 엑셀 순서가 뒤섞여 보여 실사용자가 혼란을 겪었습니다.

## 6-3. 권한 3단계

| 부르는 이름 | 코드값 | 표시 | 할 수 있는 것 |
|---|---|---|---|
| 감독자 (레벨1) | `masterLevel = 0` | 포켓보드 | 점검·입력·보고문 |
| 관리자 (레벨2) | `masterLevel = 1` | 포켓보드 PRO | + 연락처 조회·전화, 공지 작성 |
| 마스터 (레벨3) | `masterLevel = 2` | 포켓보드 Master | + 엑셀 업로드, 초기화, 접속현황, 연락처 삭제 |

⚠️ **부르는 이름과 코드값이 1씩 차이납니다.** 혼동 주의.

**인증 유지**: v2.55부터 **무기한**. 한 번 인증하면 그 기기에서 계속 유지됩니다.
(이전엔 30일 제한이 있었으나 해제 — `ADMIN_TTL` 관련 코드 전부 삭제됨)

## 6-4. 저장·병합 규칙 (데이터 유실 방지의 핵심)

여러 사람이 동시에 쓰므로, **저장할 때마다 서버 최신본과 합칩니다.**

```
저장 요청
  → 서버에서 현재 목록을 다시 읽음
  → 카드별로 updatedAt 비교
  → 더 최근 것만 남김 (mergeByUpdatedAt)
  → 합친 결과를 저장
```

`updatedAt`은 **내용이 실제로 바뀐 카드에만** 새로 찍습니다.
(안 바뀐 카드까지 찍으면 남의 최신 입력을 덮어씀)

**일일 자동정리 전에도 서버를 먼저 읽습니다** (v2.54c 버그수정)
화면을 오래 켜둔 기기가 낡은 기억으로 "하루 지났다"고 오판해
다른 사람의 방금 체크를 되돌리는 사고가 실제로 있었습니다.

## 6-5. 긴급공사

- 목록에 없는 공사를 현장에서 즉시 등록
- 5단계 마법사: 공장 → 작업위치 → 작업내용 → 작업구분 → 담당감독자
- 공사명이 **자동 조합**됨 (별도 입력칸 없음)
- **전체 공사기간이 끝나면 일반 카드와 함께 자동 삭제** (v2.54)
  - 기간 정보가 없으면 삭제하지 않음(안전 우선)

## 6-6. 접속 통계

- 기기별 임의 번호(`MMEEC_DEVICE_ID`)로 집계. **개인 식별 안 함**
- 최근 7일, 날짜별로 표시 (v2.55부터 접지 않고 전부 펼침)
- **마스터 접속은 통계에서 제외** (감독자·관리자만)
- 복수공장 설정은 **기기·날짜별 가장 최근 1건만** 집계 (중복 방지)
- 공장 조합은 축약 표기: `1~5` = 숫자, `6 PT`=`P`, `7 소재`=`소`, `8 아산`=`아`, `9 기타`=`기`
  → 예: 9개 전부 선택 시 `12345P소아기`

# 7. 보안 설계와 한계

## 7-1. 구조적 한계 — 솔직한 기록

**로그인이 없는 앱이라, 데이터를 완전히 숨길 수 없습니다.**

`config.js`는 웹에 그대로 공개됩니다. 브라우저가 써야 하는 값이라 숨길 방법이 없습니다.
따라서 주소를 아는 사람은 공개키로 공사 목록을 읽을 수 있습니다.

**할 수 있는 것 / 없는 것**

| | 상태 |
|---|---|
| 공사 목록 **삭제** 차단 | ✅ 적용됨 |
| 엉뚱한 세션 생성 차단 | ✅ 적용됨 |
| 연락처·접속기록 직접 접근 차단 | ✅ 적용됨 (함수로만) |
| 공사 목록 **읽기** 차단 | ❌ 불가 (막으면 감독자도 못 씀) |
| 공사 목록 **덮어쓰기** 차단 | ❌ 불가 (같은 이유) |

## 7-2. 접근 제한(RLS) 현황

| 테이블 | 정책 |
|---|---|
| `pocket_sessions` | SELECT 허용 / INSERT·UPDATE는 `session_id='default'`만 / **DELETE 정책 없음 = 차단** |
| 그 외 전부 | 정책 없음 = **직접 접근 전면 차단**, 함수(SECURITY DEFINER)로만 |

## 7-3. 비밀값 관리 원칙

- **Claude(AI)는 실제 코드값을 알지 않습니다.** SQL 템플릿만 만들고, 값은 실장님이 직접 채워 실행
- 마스터 코드를 바꾸면 **초기화·회사명수정 코드도 자동으로 같이 바뀝니다**
  (`admin_confirm_check`가 `master_level`을 참조하는 구조)
- 백업 토큰을 바꾸면 **`apps-script-v3.gs`도 같은 값으로 고쳐 재배포**해야 함
  (안 맞추면 백업이 조용히 실패)

## 7-4. 미해결 (BACKLOG 참고)

- 마스터 코드가 서버 함수에 **평문**으로 저장됨 (해시 아님)
- 백업 토큰도 평문
- 봇 차단·HSTS·CSP → **커스텀 도메인이 있어야 설정 가능** (현재 `pages.dev` 기본 주소라 불가)

# 8. 재구현 가이드

> 이 앱을 처음부터 다시 만들어야 할 때, 이 장의 순서대로 진행하면 됩니다.

## 8-1. 반드시 지켜야 할 설계 제약

1. **빌드 도구 쓰지 말 것** — React·Babel을 CDN으로 불러오는 단일 HTML 유지
2. **로그인 도입하지 말 것** (기획이 바뀌지 않는 한) — 현장에서 안 씁니다
3. **06시 경계는 `TZ=Asia/Seoul` 고정**
4. **구버전 데이터 호환 필수** — 옛 형식을 판별해 처리하는 폴백을 반드시 남길 것
5. **애매하면 안전한 쪽** — 지우거나 덮어쓰기보다 **유지**를 택할 것

## 8-2. 구현 순서

```
1. Supabase 프로젝트 생성 → pocket_sessions 테이블 (session_id, items jsonb, meta, updated_at)
2. RLS 설정 (7-2 표대로)
3. 관리자 함수 생성 (server/*.sql 참고, 코드값은 직접 채움)
4. public/data.js — 공장·하위공장·감독자 명단
5. public/config.js — Supabase 주소·공개키
6. public/storage.js — 저장·불러오기·병합 (6-4 규칙)
7. public/index.html — 화면 (6-1~6-6 규칙)
8. Cloudflare Pages 연결 (output directory = public)
9. 구글 앱스스크립트 (체감온도 + 백업)
```

## 8-3. 검증 필수 항목

재구현 후 아래를 **반드시 실제 데이터로** 확인:

| 항목 | 확인 방법 |
|---|---|
| 06시 경계 | 새벽 3시·오전 7시 두 시점으로 workday 계산 |
| 병합 | 두 기기가 동시에 다른 카드 수정 → 둘 다 남는지 |
| 옛 공장명 | `factory: "6.엔진"` 카드가 `6 PT` 탭에 뜨는지 |
| 정렬 | 전체 탭=엑셀순, 개별 탭=사업장순인지 |
| 권한 | 감독자에게 초기화 버튼이 안 보이는지 |
| 긴급공사 | 기간 종료 후 자동 삭제, 기간 없으면 유지 |
