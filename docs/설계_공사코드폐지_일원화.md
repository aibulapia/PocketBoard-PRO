# 설계: 공사 코드 폐지 → 데이터 일원화 (2026-08-08 확정)

> 상태: ✅ **v2.5c에서 구현 완료** (2026-08-10 확인).
> 이 문서는 당시 설계 판단의 근거를 남긴 기록이며, 새로 할 작업은 없습니다.
> 구현 내용: 공사 코드 개념 폐지 → 저장소를 `default` 하나로 일원화
> 배경: v2.5a 사용 중 "마스터 모드에서 공사 코드 삭제하니 TODAY 초기화됨" 문제 제보.
> 원인 분석 결과 구조 자체를 바꾸기로 결정.

---

## 1. 문제의 뿌리

### 지금 구조 (잘못된 것)
```
공사 코드 = 완전히 별개의 데이터 저장소 (칸막이)

  5p       → pocket_sessions['5p']       (107건 + TODAY 27건)
  default  → pocket_sessions['default']  (107건 + TODAY 0건)
  0909     → pocket_sessions['0909']     (107건 + TODAY 0건)
```
- 코드를 바꾸면 **다른 저장소로 이동** → 방금 한 TODAY 체크가 안 보임
- 실제로는 "초기화"가 아니라 "체크 없는 다른 세션으로 전환"된 것
- 실측: `5p`에 todayOn 27건, `default`·`0909`엔 0건 (완전 분리 확인됨)

### 실장님이 원하는 개념 (올바른 것)
```
데이터는 무조건 한 곳에 전부 저장.
"코드"나 "내 공장"은 그 위에서 화면만 거를 뿐, 저장을 나누지 않는다.
권한 레벨은 보이는 범위 차이일 뿐, 데이터는 공유.
```

### 결정적 발견
- **이미 있는 `🏭 내 공장` 필터가 정확히 이 올바른 동작을 하고 있음.**
  - 화면만 거름(localStorage에 공장 목록만 저장), 데이터는 안 나눔
  - 내 공장을 바꿔도 TODAY 안 사라짐 (데이터를 안 건드리므로)
- 즉 **공사 코드는 내 공장과 기능이 겹치면서, 추가로 "데이터까지 쪼개는" 해로운 짓을 함**

### 결정
**공사 코드 개념을 완전히 폐지하고, 공장 필터는 `🏭 내 공장`으로 일원화한다.**

## 2. 목표 구조

```
        pocket_sessions['default']  ← 단 하나의 저장소, 모든 기록 여기에
                    │
        화면 필터 (데이터 안 건드림)
                    ├─ 공장 탭 (전체 / 1공장 / 2공장 …)
                    └─ 🏭 내 공장 설정 (기기별, 담당 공장만)
```

- 세션 ID는 코드에 **`"default"` 고정** (또는 상수 하나)
- 사용자는 더 이상 코드를 입력하지 않음
- TODAY·감독자·메모 등 모든 입력이 한 곳에 쌓임 → 누가 어디서 체크하든 전원 공유
- 코드를 바꾸거나 지울 개념 자체가 없어지므로, 제보된 문제가 원천 소멸

### 3-2. 유지 (건드리지 않음)
- `🏭 내 공장` 필터 로직 전체 (myFactories) — 이게 새 주력 필터
- 공장 탭 (activeTab)
- storage.js의 저장/불러오기 — 단 sessionId를 항상 "default"로 고정

### 3-3. storage.js 수정
- `getSessionId()`: URL·localStorage 참조 제거, **항상 `"default"` 반환**
- `setSessionId()`: 사실상 무의미해지므로 제거 또는 no-op
- 나머지(load/save/mergeItems/realtime)는 sessionId가 "default"로 고정될 뿐 로직 유지

### 3-4. 서버(Supabase) — 별도 작업
- `session_registry` 테이블, `master_*_session` RPC 3종은 더 이상 안 쓰임
  → 당장 삭제할 필요는 없음(안 부르면 그만). 정리는 나중에
- ⚠️ **자동 백업이 `session_registry` 기반**이므로(backup_export), 코드 폐지와 별개로
  백업이 `default` 세션을 포함하도록 재확인 필요 (기존 BACKLOG 검토항목 D와 연결)

## 4. ⚠️ 데이터 마이그레이션 (가장 조심할 부분)

지금 `5p`에 **최신 데이터(TODAY 27건 포함)**가 있고, `default`는 옛날 것이다.
코드를 "default 고정"으로 바꾸면, 자칫 최신 `5p` 데이터를 버리고 옛 `default`를 보게 된다.

**착수 시 반드시 지킬 순서:**
1. 먼저 어느 세션이 최신·정본인지 실장님과 확정 (현재로선 `5p`가 유력)
2. 그 정본 데이터를 `default`로 복사(덮어쓰기)
3. 그 다음에 코드 배포 (default 고정)
4. 배포 후 실제 폰에서 TODAY·감독자·메모가 그대로인지 확인

> 이 순서를 어기면 최신 입력이 날아갈 수 있음. 마이그레이션 SQL은 착수 시점에
> 실제 데이터를 다시 조회해서 작성한다(그 사이 데이터가 또 바뀔 수 있으므로).
